How microservices communicate

Three mechanisms — each for a different job.

1 · Sync REST

Browser → Gateway → service

JWT (HS256) validated at gateway + service. JwtBlacklistMiddleware checks Redis JTI on logout. X-Correlation-Id propagated by interceptor + middleware.

2 · Sync gRPC

Ledger → Customer :6102

Reserve / Commit / Credit / Release with 3s deadlines. Failure maps to 503 CUSTOMER_UNAVAILABLE. Hold ID must equal transaction ID (idempotency).

3 · Async events

via RabbitMQ topic

Exchange smartbank.ledger, routing key ledger.transferred. Customer + Notification (+ future Risk) each own a durable queue + DLX.

Sequence · money transfer

POST /api/transfers (idempotent)

sequenceDiagram
  participant UI as SPA
  participant GW as Gateway :5100
  participant LE as Ledger :5103
  participant CU as Customer gRPC :6102
  participant MQ as RabbitMQ
  participant NO as Notification :5105
  UI->>GW: POST /api/transfers + Idempotency-Key
  GW->>LE: forward + JWT
  LE->>LE: Redis idempotency check
  LE->>CU: ReserveFunds(hold_id=txId, 3s)
  CU-->>LE: ok + available_balance
  LE->>LE: write journal + outbox row
  LE->>CU: CommitFunds / CreditFunds
  LE->>MQ: publish MoneyTransferred (outbox dispatcher)
  MQ-->>CU: customer.ledger.transferred
  MQ-->>NO: notification.ledger.transferred

If Customer is down: 503 CUSTOMER_UNAVAILABLE. Retries are safe — reserve is idempotent on hold_id and transfers are idempotent on Idempotency-Key (Redis). Ledger's outbox table guarantees the event is published even if the broker was briefly down.

Sequence · login + MFA

POST /api/auth/login

sequenceDiagram
  participant UI as SPA
  participant GW as Gateway
  participant ID as Identity :5101
  participant RD as Redis
  UI->>GW: POST /api/auth/login (email+password)
  GW->>ID: forward (anonymous route)
  ID->>ID: verify hash (ASP.NET Identity)
  ID->>RD: store MFA challenge + OTP
  ID-->>UI: 200 mfaRequired + challengeId
  UI->>ID: POST /mfa/verify (challengeId+code)
  ID->>RD: check + delete challenge
  ID-->>UI: access + refresh tokens (15m / 14d)

Logout writes the token JTI into Redis; gateway and services reject it afterwards. Local E2E seam: GET /api/auth/e2e/otp?email=… only when E2E_OTP_SEAM=true.
